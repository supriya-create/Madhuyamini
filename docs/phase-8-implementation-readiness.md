### 3.2 Critical path

`8.0 → 8.1 → 8.2 → 8.3 → 8.9` for the returns stream, because exchanges need settlement and settlement needs the returns core; in parallel `8.0 → 8.5 → 8.6 → 8.7 → 8.8 → 8.9` for commissions, with 8.8 also depending on 8.2 (returnable commissions use the returns arithmetic). The longest chain is the commission stream (five steps after 8.0) if it runs alone; with two engineers the elapsed critical path is `8.0 → 8.5 → 8.6 → 8.7 → 8.8 → 8.9`, and 8.8 cannot complete before 8.2.

### 3.3 Parallel work

- After 8.0, the two streams touch disjoint tables, services, pages and policy files. They share only: `routes.ts` additions, `capabilities.ts` additions, `outbox.ts` kinds, the `redact.ts` allow-list, the jobs registry and `vercel.json`. Those are list edits; merge conflicts are trivial, but each stream's step must land with the full `npm run check` after rebasing on the other.
- Within the returns stream, 8.4 can run alongside 8.3 (both depend on 8.2 only).
- 8.9 waits for both streams.

## 6. Rollback strategy

| Level                         | Procedure                                                                                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Code only (a step misbehaves) | Revert the step's commit; the additive schema stays. Columns default to `STANDARD` / `CATALOGUE` / `NULL`; no existing path reads the new tables, so the application runs as before. Jobs for the step are unregistered by the revert.                                                                          |
| Schema (a migration must go)  | Apply the migration's `rollback.sql` by hand as the migration owner, then delete its `_prisma_migrations` row, in reverse step order. `phase8_returns` cannot be rolled back while `refunds.return_request_id` rows exist: export and null the column first (the file documents it); enum values remain unused. |
| Data (a settlement was wrong) | Nothing is edited: a correction is a new audited operation (ADMIN `returns.correct`), an additional refund within the caps, or a manual refund record; the audit log and refund lines keep the original.                                                                                                        |
| Rehearsal                     | Each step's migration and rollback are applied and re-applied on a scratch database before the step's commit, as the Phase 7 steps did.                                                                                                                                                                         |
