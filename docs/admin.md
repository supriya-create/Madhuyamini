# Madhuyamini — Admin Dashboard and Store Operations (Phase 7)

Status: **Proposed, awaiting approval** · 1 Nov 2026, revision 3 (approved in principle, final refinements incorporated) · Nothing in this document has been implemented or tested.

Revision 2 incorporates the owner's eight refinements: a second factor required of every staff session with enrolment verification, one-time recovery codes, replay protection, rate limits and re-authentication (§5.9); payment and fulfilment states kept independent with explicit, audited cash-on-delivery transitions (§5.10); masked, permission-controlled customer data (§5.7); audit rows that survive rolled-back mutations without secrets or needless PII (§6); hardened Cloudinary uploads (§5.2); concurrency-safe last-admin protection and session revocation (§6, §7.1); production safeguards for the promote script (§13); inventory adjustments that record reason, actor and before/after quantities (§3, §5.3).

Revision 3 incorporates the owner's final refinements: delivery failure and return-to-origin as a workflow in which stock returns only after physical return and inspection (§5.11); atomic replay prevention and recovery-code consumption under concurrency (§6 A13, §7.1); the audit log protected by database privileges as well as the trigger (§3, §13); scoped, time-limited, revocable reveal grants (§5.7); folder-scoped orphan cleanup after a grace period driven by an upload ledger (§5.2, §6 A17); and authorisation plus second-factor checks inside every protected data access and mutation (§6). A final implementation checklist (§15) and the remaining production blockers (§16) close the document.

Scope: a role-gated admin area for running the shop day to day — overview, catalogue (products, categories, variants, images), inventory, orders and fulfilment, payment and refund investigation, background-job and webhook monitoring with safe retries, customers, reports, audit logging and admin two-factor sign-in. Everything money- or stock-related calls the Phase 5–6 services; the admin adds authorisation, confirmation, evidence and an audit trail around them. Out of scope: coupons, reviews moderation, returns, custom-artwork requests (Phase 8); content pages (Phase 9); CSP and monitoring (Phase 10).

Related: [checkout.md](checkout.md) (orders, payments, jobs), [cart.md](cart.md), [auth.md](auth.md), [data-model.md](data-model.md), [architecture.md](architecture.md) §7.

## 1. Gaps and risks found during inspection

1. **No staff user exists.** Nothing creates an ADMIN; registration always yields CUSTOMER. A promotion script and a dev-seed admin are needed before any admin page is reachable.
2. **No fulfilment states.** `OrderStatus` stops at `CONFIRMED`; orders cannot be marked processing, shipped or delivered, and COD attempts cannot be marked collected. The enum must grow (an online `ALTER TYPE … ADD VALUE`).
3. **Admin cancellation of a confirmed order has no path.** Stock was consumed at confirmation; cancelling must put it back and, for online orders, queue a refund. `releaseOrderHolds` does not cover this; a `restockForOrder` is needed.
4. **NEEDS_REVIEW orders have no exit** other than the transition table's `admin_confirmed`/`admin_cancelled` edges, which nothing calls. Resolution must be built so that confirmation is impossible without a captured attempt (provider evidence).
5. **No write path for the catalogue** and no Cloudinary credentials (`image-loader.ts` only rewrites delivery URLs). Uploads need `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` and signed upload parameters generated server-side.
6. **Queue rows marked FAILED stay failed forever**; the only recovery today is SQL. Retrying must reset the row for the worker rather than re-implementing the worker.
7. **Webhook payloads contain PII** (email, phone, UPI id). The ledger viewer must mask them for STAFF.
8. **Inventory CHECK `reserved <= stock_on_hand`**: an adjustment that lowers stock below current holds must be refused with a clear message, not a constraint error.
9. **Role changes must revoke sessions** (auth.md P4 promised rotation on privilege change); Better Auth has no hook for our role column, so the admin service deletes the user's sessions itself.
10. **Better Auth's `admin` plugin** (ban, impersonate, set role) is deliberately **not** used: it would move role authority out of our data layer and add impersonation, which the brief does not want.
11. **Two-factor sign-in**: Better Auth ships a `twoFactor` plugin, but it ties enforcement to a user flag and keeps no per-session proof, accepted-step record or re-authentication window. The gate needs all three, so Phase 7 implements RFC 6238 itself over `node:crypto` (§5.9), leaving password sign-in and sessions to Better Auth.
12. **Reports must never claim what cannot be computed**: revenue counts only `CONFIRMED`-and-beyond orders with captured or COD payments; "best-selling" stays internal until Phase 9 decides to show it.
13. **Vercel Hobby crons are daily** (checkout.md): the monitoring pages make slow sweeps visible, but production needs a scheduler (§13).
14. **One database role does everything today.** The application connects as the table owner, so no privilege can stop it from editing the audit log; Phase 7 introduces a runtime role (`madhuyamini_app`) without `UPDATE`/`DELETE` on append-only tables and a separate migration connection (§3, §13).
15. **No notion of a failed delivery.** A refused or undeliverable parcel has no state; without one, the tempting shortcut is to restock on refusal. §5.11 adds `DELIVERY_FAILED` and `RETURNED` so stock only returns after inspection.

/// Append-only (refinement 4 of revision 2, refinement 3 of revision 3): an
/// immutability trigger AND no UPDATE/DELETE privilege for the runtime role.
model AdminAuditLog {

  actorId    String?      @map("actor_id") @db.Uuid     // null only for scripts and system sweeps (see actorLabel)

  actorRole  UserRole?    @map("actor_role")

  targetId   String?      @map("target_id")
  outcome    AuditOutcome
  reason     String?
  errorCode  String?      @map("error_code")
  grantId    String?      @map("grant_id") @db.Uuid     // the staff_pii_grants row a reveal relied on

  after      Json?

/// Who may change stock and why. System restocks exist only for cancellations
/// of unshipped orders; everything that came back physically goes through an
/// inspection with an actor (refinement 1).
enum InventoryAdjustmentKind { RECEIVED  CORRECTION  WRITE_OFF  RESTOCK_ON_CANCEL  RESTOCK_ON_RETURN }

model InventoryAdjustment {
  id             String                  @id @default(uuid(7)) @db.Uuid
  variantId      String                  @map("variant_id") @db.Uuid
  kind           InventoryAdjustmentKind

  stockBefore    Int                     @map("stock_before")  // CHECK >= 0
  stockAfter     Int                     @map("stock_after")   // CHECK = stock_before + delta AND >= reserved_at_time
  reservedAtTime Int                     @map("reserved_at_time")
  reason         String                                        // CHECK length(btrim(reason)) >= 3
  actorId        String?                 @map("actor_id") @db.Uuid   // required unless kind = RESTOCK_ON_CANCEL (CHECK)
  orderId        String?                 @map("order_id") @db.Uuid   // required for RESTOCK_ON_CANCEL and RESTOCK_ON_RETURN (CHECK)
  auditId        String?                 @map("audit_id") @db.Uuid
  createdAt      DateTime                @default(now()) @map("created_at")
  variant ProductVariant @relation(fields: [variantId], references: [id], onDelete: Restrict)
  @@index([variantId, createdAt])
  @@index([orderId])
  @@map("inventory_adjustments")
}

model Shipment {

// --- Customer-data reveal grants (refinement 4). ---

/// A scoped, time-limited permission for one staff member to reveal contact
/// details; checked at request time on every render, so revocation is immediate.
model StaffPiiGrant {
  id          String    @id @default(uuid(7)) @db.Uuid
  granteeId   String    @map("grantee_id") @db.Uuid
  grantedById String    @map("granted_by_id") @db.Uuid
  /// Null = any customer (support shift); otherwise one customer.
  customerId  String?   @map("customer_id") @db.Uuid
  fields      String[]                                   // subset of: email, phone, address
  reason      String                                     // CHECK length >= 3
  expiresAt   DateTime  @map("expires_at")               // CHECK <= created_at + 24 h (policy ceiling in SQL)
  revokedAt   DateTime? @map("revoked_at")
  revokedById String?   @map("revoked_by_id") @db.Uuid
  createdAt   DateTime  @default(now()) @map("created_at")
  grantee   User @relation("piiGrantee", fields: [granteeId], references: [id], onDelete: Cascade)
  grantedBy User @relation("piiGrantor", fields: [grantedById], references: [id], onDelete: Restrict)
  @@index([granteeId, expiresAt])
  @@map("staff_pii_grants")
}

/// One reveal: which grant, which customer, which fields, until when. Rendered

model StaffPiiReveal {

  customerId String   @map("customer_id") @db.Uuid
  fields     String[]
  reason     String
  expiresAt  DateTime @map("expires_at")                 // created_at + adminPolicy.pii.revealMinutes

  @@index([staffId, expiresAt])
  @@index([customerId, createdAt])
  @@map("staff_pii_reveals")
}

## 5. Feature design

### 5.1 Overview (business dashboard)

Server-rendered stat cards and lists, all from existing tables: orders and revenue today / 7 days / 30 days (confirmed-and-beyond, captured or COD), orders awaiting payment, awaiting fulfilment (`CONFIRMED` + `PROCESSING`), `NEEDS_REVIEW` count, FAILED queue rows (outbox, webhooks, refunds), low-stock variants, last job runs (derived from queue rows' `claimed_at` — no new table). Links go to the filtered lists. Nothing is estimated; empty states say "no orders yet".

### 5.2 Catalogue

- **Products:** list (status, category, variants, stock, updated); create/edit form (title, slug — generated from the title, editable, uniqueness checked server-side; subtitle; description; techniques ≥ 1; construction methods; material; care; category; one-of-a-kind; featured; SEO fields; HSN/tax rate kept nullable per D7c). **Publish** (`DRAFT → ACTIVE`, ADMIN; requires ≥ 1 active variant with price and ≥ 1 image with alt) and **archive** (`ACTIVE → ARCHIVED`; carts flag the lines, Phase 5). Hard delete per A3.
- **Options and variants:** define option axes and values; create variants per combination; SKU (unique, immutable once an order item references it), price in rupees converted to paise on the server, compare-at, weight, active flag. A variant with order items or cart lines cannot be deleted (Restrict already) — deactivate instead.
- **Images (hardened signed uploads, refinement 5):** the server issues a short-lived signature only to staff holding `catalogue.images`, binding `timestamp`, a fixed `folder` (`madhuyamini/products/<productId>`), a server-generated `public_id`, `resource_type=image`, `allowed_formats=jpg,png,webp,avif`, an incoming transformation `c_limit,w_4000,h_4000`, and a **signed upload preset** that enforces the byte ceiling and minimum/maximum dimensions at Cloudinary. The browser uploads directly (nothing is proxied) with `accept` and a client-side size check as a courtesy only. On completion the server **verifies Cloudinary's response signature** (`public_id` + `version` under the API secret) and checks `resource_type`, `format`, `bytes`, `width`, `height` and `folder` against `adminPolicy.uploads` (min 800×800, max 6000×6000, ≤ 8 MB, formats above) before storing `url`, `publicId`, `width`, `height` and the required `alt`. Anything else is refused and nothing is stored. Every signature is recorded in `product_image_uploads` (`ISSUED`, public id, folder, staff); a successful attach flips the row to `ATTACHED` in the same transaction. Ordering and variant assignment are plain updates; removal deletes the row, marks the ledger `DISCARDED` and destroys the asset at Cloudinary afterwards (best effort, audited, retried by the sweep). **Orphans** are handled only from the ledger: the daily sweep destroys public ids still `ISSUED` after `adminPolicy.uploads.orphanGraceHours` (24), each necessarily inside `madhuyamini/products/` (CHECK), never by listing the account, and records each deletion as `system:upload-sweep` (§6 A17, §7.1). Signatures are valid for Cloudinary's one hour.
- **Categories:** tree with position, activate/deactivate, move under another parent (cycle check), delete only when no products and no children (Restrict already).

### 5.3 Inventory

- Levels table (variant, product, SKU, on hand, reserved, available, threshold) with low-stock filter.
- **Adjust** (STAFF): kind RECEIVED / CORRECTION / WRITE_OFF, signed delta, reason required (≥ 3 characters). Transaction (A3): lock the inventory row (`lockInventoryRows`), read `stock_on_hand` and `reserved`, refuse unless `stock_on_hand + delta >= reserved` and `>= 0`, update, insert `inventory_adjustments` with `stockBefore`, `stockAfter`, `reservedAtTime`, `reason`, `actorId` and the audit row id, then the SUCCESS audit row. Refusals say how many units are held by pending orders and are audited `REFUSED`. The adjustment history is shown per variant with who, when, why and the quantities before and after.
- Threshold edit per variant.
- No direct edit of `reserved`: it only moves through the Phase 6 service.

### 5.4 Orders and fulfilment

State additions and edges (pure `transitions.ts`, extended):

```
CONFIRMED ──start_processing──► PROCESSING ──ship──► SHIPPED ──deliver──► DELIVERED
SHIPPED ──delivery_failed──► DELIVERY_FAILED ──parcel_returned──► RETURNED ──inspection_completed──► CANCELLED   (§5.11; stock only via inspection)
DELIVERY_FAILED ──carrier_lost_confirmed──► CANCELLED                                                            (write-offs, refund intent)
CONFIRMED / PROCESSING ──admin_cancelled──► CANCELLED      (system restock + refund intent if paid online)
NEEDS_REVIEW ──admin_confirmed (captured attempt required)──► CONFIRMED
NEEDS_REVIEW ──admin_cancelled──► CANCELLED               (refund intent if captured)
```

- **List:** filters by status, payment method, date range, search by order number / email / name; sorted newest first; paginated by URL params (server-rendered, like the catalogue listing).
- **Detail:** everything the customer sees (full exposure) plus attempts with provider ids, refunds, reservations, the full event timeline, audit entries for this order, and actions allowed in the current state.
- **Start processing** (STAFF): `CONFIRMED → PROCESSING`, event.
- **Ship** (STAFF): form with carrier, tracking number, URL; transaction: lock order, transition, insert shipment, event, outbox `order.shipped`.
- **Deliver** (STAFF): sets `deliveredAt`, transition, event, outbox `order.delivered`; for COD also offers **Cash collected** (see 5.5).
- **Cancel** (ADMIN; STAFF may cancel `PENDING_PAYMENT` only): confirmation page requiring a reason and the typed order number. Transaction: lock order; if `PENDING_PAYMENT` → `releaseOrderHolds`; if `CONFIRMED/PROCESSING` → `restockForOrder` (new inventory function: conditional `stock_on_hand += q` per item, `inventory_adjustments` RESTOCK_ON_CANCEL); if a captured online attempt exists → refund intent row (reason `cancelled_by_shop`) through the Phase 6 queue; status `CANCELLED` with `cancellationReason = ADMIN`; event; outbox `order.cancelled` (reason "shop"); audit. Cart stays as it is.
- **Staff note** (STAFF): an `order_events` row with `type = "note"`, actor STAFF/ADMIN; shown only in the admin.

### 5.6 Operations: jobs, webhooks, notifications

- **Jobs page:** per job: last claim time and counts from the queue tables; "Run now" (ADMIN) calls `runJob(name)` in the request (same lease rules as the cron, so overlapping runs are safe) and shows the summary; audited.
- **Outbox:** list by status with filters; FAILED rows show `lastError`; **Retry** (STAFF) resets `status = PENDING, attempts = 0, nextAttemptAt = now, claimedAt = null` (dedupe key unchanged, so a duplicate send is still impossible by key); **Discard** (ADMIN, reason) sets `FAILED` with a note. Payloads shown; recipients masked for STAFF.
- **Webhook ledger:** list, filter by type/status, payload viewer with PII masked for STAFF (email, contact, vpa, card fields); **Re-apply** (ADMIN) resets to `RECEIVED` for `process-webhooks` (the handler is idempotent).
- **Refund queue:** INITIATED / REQUESTED / FAILED with provider ids; retry per 5.5.
- **Alerts:** the `ops.alert` outbox rows as an inbox with "acknowledge" (audit only).

### 5.7 Customers (masked by default, refinements 3 and 4)

- **List and search** (STAFF): search by order number, or by exact email or phone (the input is normalised and hashed for the lookup; the list never shows what was typed back). Rows show name, masked email (`a***@example.com`), masked phone (last four digits), role, verification state, order count, city of the default address. No address lines, no full contact details.
- **Detail** (STAFF): the same masked identity, orders (number, status, total, date), verification state, session count. Addresses show recipient name, city, state and PIN only.
- **Grants** (`staff_pii_grants`, ADMIN with re-auth): an ADMIN grants a named staff member the right to reveal specific fields (`email`, `phone`, `address`), for one customer or for any customer during a support shift, for a stated reason, for at most 24 hours (SQL-enforced ceiling; the default form offers 2 hours). Grants are listed on the customer and staff pages and in the audit browser; **revocation is immediate**: every reveal and every render re-reads the grant row (`revoked_at IS NULL AND expires_at > now()`), nothing is cached, and revoking a grant also ends any reveal that relied on it. The owner inbox is notified of each grant.
- **Reveal** (STAFF with an active grant covering the customer and fields, or ADMIN inherently): an explicit action with a reason that writes a `staff_pii_reveals` row (grant id, fields, expiry = `adminPolicy.pii.revealMinutes`, 10) and an audit row `customer.pii.reveal` carrying the grant id. The page shows unmasked fields only while an unexpired reveal exists **and** its grant is still active; after that the fields mask again without any further action. Reveals are counted on the overview ("reveals this week") and listed per customer.
- **Order fulfilment needs the address:** on an order detail in `CONFIRMED`, `PROCESSING`, `SHIPPED`, `DELIVERY_FAILED` or `RETURNED`, STAFF see the delivery address and phone of that order (operational necessity, logged once per order as `order.address.view` the first time a given staff member opens it); on `DELIVERED` or `CANCELLED` orders they are masked again.
- **Set role** (ADMIN; sensitive → re-auth): cannot target self; cannot demote the last ADMIN (serialised, §6); revokes every session, staff verification and PII grant of the target in the same transaction; audited with before/after roles; an `ops.role_changed` email goes to the owner inbox.
- **Reset a staff member's two-factor** (ADMIN; sensitive): deletes their `staff_two_factor`, recovery codes and session verifications so they enrol again at next sign-in; audited; owner notified.
- **Resend verification email** (STAFF): reuses the Phase 4 rate-limited action.
- No deletion, export or impersonation (A8); DPDP export and erasure are Phase 8/10.

### 5.8 Reports

Parameterised SQL in `features/admin/reports/data.ts`, each with a unit-tested shape and an integration test against fixtures:

- **Sales:** orders, units, gross revenue (paise) per day/week/month; by payment method; cancelled and refunded amounts; average order value. Definition: revenue = `total_in_paise` of orders in `CONFIRMED`, `PROCESSING`, `SHIPPED`, `DELIVERED` whose payment is `CAPTURED` (online) or collected (COD), minus processed refunds.
- **Products:** units and revenue per product/variant for a period (from `order_items`), with no claim of "best-selling" on the storefront until Phase 9.
- **Inventory:** on hand, reserved, available, value at current price, low stock, adjustments in period.
- **Operations:** payment success rate by attempt, time from placement to capture, late captures, refund totals, failed-job counts.
- **CSV export** (ADMIN): route handler `GET /admin/reports/export?report=…&from=…&to=…` streaming text; audited.

### 5.9 Staff sign-in, two-factor and re-authentication (refinement 1)

**Why an own implementation rather than Better Auth's `twoFactor` plugin:** the plugin ties enforcement to the user's `twoFactorEnabled` flag and finishes the sign-in once a code is accepted; it keeps no per-session proof, no accepted-step record for replay protection, and no notion of a re-authentication window. The admin gate needs all three. RFC 6238 is thirty lines over `node:crypto` (HMAC-SHA1, 30-second steps, six digits, ±1 step tolerance), tested against the RFC's published vectors; secrets are encrypted at rest; Better Auth continues to own password sign-in and sessions.

**Enrolment** (`/account/security/two-factor`, any STAFF/ADMIN account; CUSTOMER accounts have no second factor):

1. Password re-entry (Better Auth sign-in check without creating a session) → a new secret is generated, encrypted with `ADMIN_TOTP_KEY` (AES-256-GCM, `keyVersion`), stored with `enabledAt = null`, and shown once as a QR code and text (`otpauth://totp/Madhuyamini:<email>?secret=…&issuer=Madhuyamini&digits=6&period=30`).
2. **Enrolment verification:** the user must enter a current code; only then is `enabledAt` set and `lastAcceptedStep` recorded. An unverified enrolment is discarded after `adminPolicy.enrolmentMinutes` (15) and never satisfies the gate.
3. **Recovery codes:** ten codes of ten characters from the unambiguous alphabet, generated once, shown once, stored as scrypt hashes; each is single-use (`usedAt`). Regeneration requires a fresh TOTP code and invalidates the old set; using a recovery code emails the user and the owner inbox.

**Every staff session must verify** (not merely users with the flag): after password sign-in, `/login/verify` asks for a code; success writes `staff_session_verifications` for the current session id. `requireStaffSession()` refuses `/admin/*` and every admin action when the row is missing — a STAFF/ADMIN account that has not enrolled is sent to enrolment first, and an account whose enrolment was reset by an ADMIN is sent there again. Sessions created before enrolment, or on another device, each need their own verification. The storefront account area keeps working without it (staff are also customers).

**Replay protection:** a submitted TOTP code is accepted only if its time step is greater than `lastAcceptedStep`; the step is recorded in the same transaction as the verification row. The same code, or any code from an earlier step, is refused even if mathematically valid. Recovery codes are consumed atomically (`UPDATE … WHERE used_at IS NULL RETURNING`).

**Rate limiting** (through the Phase 4 limiter; keys hashed): TOTP attempts 5 per 15 minutes per user and 20 per 15 minutes per IP; recovery-code attempts 3 per hour per user; enrolment restarts 3 per hour per user; re-authentication prompts share the TOTP limits. Limits lapse with the window; there are no permanent lockouts, but five failed recovery attempts email the owner inbox.

**Re-authentication for sensitive operations:** permissions marked `reauth` in the matrix (refunds, attach payment, accept mismatch, cancel confirmed orders, role changes, 2FA resets, run-now, discard, hard delete, CSV export, PII reveal grants) require the session's `verifiedAt` to be within `adminPolicy.reauthWindowMinutes` (10). Otherwise the action redirects to `/admin/reauth?next=…`, which asks for a fresh code and refreshes `verifiedAt`; the pending form is then resubmitted by the user (no replay of the original request).

**Key handling:** `ADMIN_TOTP_KEY` is required for any staff sign-in; rotation decrypts with `ADMIN_TOTP_KEY_PREVIOUS` by `keyVersion` and re-encrypts on next verification. The key never leaves the server; secrets are never logged or included in audit snapshots (the redactor drops them).

### 5.10 Payment status and fulfilment status are independent (refinement 2, revision 2)

Two machines, two tables, no shared columns: `Order.status` is the **fulfilment lifecycle**; `Payment.status` is the **money lifecycle** of each attempt (`INITIATED → CREATED → AUTHORIZED → CAPTURED → REFUNDED`, `FAILED`). The only couplings are the Phase 6 rule that an online order becomes `CONFIRMED` when a capture is applied, and the Phase 7 rule that cancelling or returning a captured order queues a refund. Fulfilment actions never write `payments`; payment actions never advance fulfilment beyond `CONFIRMED`.

**Cash on delivery** has its own explicit payment transitions, applied by `applyCodEvent(attemptId, event, facts)` in `features/payments` (reused by the admin, never reimplemented):

| Event                     | From → To            | Who             | Preconditions                                                                                                       | Effects                                                                                                                                                                    |
| ------------------------- | -------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cod_collected`           | `CREATED → CAPTURED` | STAFF           | order `DELIVERED` (or `SHIPPED` with reason "collected at handover"); amount entered equals `amountInPaise` exactly | `capturedAt`, `collectedById` on the attempt; order event `payment.cod_collected`; audit; revenue reports count the order from this moment                                 |
| `cod_refused`             | `CREATED → FAILED`   | STAFF           | order `SHIPPED`; reason required                                                                                    | attempt `FAILED` with `failureCode = COD_REFUSED`; **no stock change**; the order enters the return-to-origin workflow (§5.11) as `DELIVERY_FAILED`; audit; owner notified |

Partial collection is refused (the amount must match). Nothing here moves inventory: money and stock are changed by different, separately audited transitions.

### 5.11 Delivery failure and return to origin (refinement 1, revision 3)

A parcel that is refused, unclaimed, undeliverable or lost does **not** put stock back. Stock returns only when the goods are physically back and inspected, through the audited adjustment path (A3) with an actor, a reason and before/after quantities. The workflow applies to any shipped order — COD refusal is one trigger — and is the foundation Phase 8 reuses for customer-initiated returns.

```

Inventory untouched.                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

Reports show returned and written-off units and the refunds they caused; the overview lists orders in `DELIVERY_FAILED` and `RETURNED` awaiting action. Nothing in this workflow uses `releaseOrderHolds` or the Phase 6 system restock: those remain for unshipped cancellations only.

## 6. Transaction boundaries, audit atomicity and lock order

**Authorisation inside every protected access (refinement 6).** The admin layout's check is a convenience, not the control. Every admin data function and service takes a `StaffContext` as its first argument — a branded value created in exactly one place, `requireStaffSession()`, which verifies the role **and** the session's second-factor row in the database on that request. Data functions in `features/admin/**/data.ts` never accept a bare user id and never read `getCurrentUser()` themselves; services call `requirePermission(ctx, capability)` and, where flagged, `requireReauth(ctx)` before touching data, and reads (lists, reports, exports, payload views) are gated the same way as writes. Two guards keep this true over time: a unit test scans every exported function in `features/admin/**/{data,service}.ts` and fails if its first parameter is not `ctx: StaffContext`, and the integration suite calls every action and service with no context, a forged context, a CUSTOMER context, a STAFF context without a verification row, and a STAFF context for ADMIN-only capabilities — each must refuse and leave a `REFUSED` audit row.

**Audit atomicity (refinement 4, revision 2).** `runAudited({ ctx, action, target, capability }, work)` is the one entry point for admin mutations:

1. Authorisation and re-authentication are checked first. A refusal writes a `REFUSED` audit row in its **own** transaction and throws `ForbiddenError`; nothing else runs.
2. `work(tx)` runs inside one database transaction that ends with the `SUCCESS` audit row — the change and its record commit together or not at all.
3. If `work` throws, the transaction has rolled back; `runAudited` then writes a `FAILED` row in a **separate** transaction (action, target, `errorCode`, hashed IP — never the message, stack, or input) and rethrows.
4. Snapshots pass through an allow-list redactor per target type; the audit insert failing fails the operation by design. The table cannot be updated or deleted by the runtime role (§3, §13).

**Global lock order** extends checkout.md §5.5: `carts → orders → payments/refunds → inventory (ascending variant id) → reservations`; catalogue writes lock `products → product_variants → inventory`; role changes take an **advisory transaction lock** (`pg_advisory_xact_lock(hashtext('user-roles'))`) before locking the target `users` row; two-factor operations use **conditional single-row updates** rather than locks (A13). No transaction calls the provider, Cloudinary or email; those calls happen before (evidence, signatures) or after (best-effort deletes).

| ID   | Transaction                               | Locks / atomic predicate                                                                                                                                                                                                                                                                                                        | Writes                                                                                                                                                                         | Outside                                                            |
| ---- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| A1   | Product / variant / category save         | product (and variants)                                                                                                                                                                                                                                                                                                          | row updates, slug/SKU uniqueness by index, SUCCESS audit                                                                                                                       | —                                                                  |

## 7. Security risks and controls

| Risk                                             | Control                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Staff session without a second factor            | `requireStaffSession` demands a verification row for the current session; no flag on the user can substitute. Enrolment counts only after a code verifies. Covered by tests that use a valid STAFF session with no verification.                                                                                                                                                                                                             |
| Authorisation only at the layout                 | Every admin data and service function takes a `StaffContext` built only by `requireStaffSession`; a signature-scan unit test and a forged-context integration suite enforce it (§6).                                                                                                                                                                                                                                                         |
| TOTP replay, concurrent submissions, brute force | Acceptance is a single conditional UPDATE on `last_accepted_step` (one winner among concurrent requests with the same code); codes from the same or an earlier step refused; recovery codes consumed by a conditional UPDATE (`used_at IS NULL`); 5 attempts per 15 minutes per user, 20 per IP; recovery 3 per hour; alerts on recovery use and repeated failures.                                                                          |
| TOTP secret exposure                             | AES-256-GCM under `ADMIN_TOTP_KEY` with key versioning; redactors drop ciphertext and codes from audits; the key is never in logs or snapshots; QR shown once at enrolment.                                                                                                                                                                                                                                                                  |
| Stolen staff session                             | Sensitive operations need a fresh code within the re-auth window; the security page lists sessions; password change revokes the others (Phase 4); role change and 2FA reset revoke everything; `Cache-Control: private, no-store` on admin responses.                                                                                                                                                                                        |
| Privilege escalation                             | `role` never from input; `setRole` ADMIN-only, re-auth, cannot target self, cannot remove the last ADMIN (advisory lock + trigger); sessions revoked in the same transaction; audited; `proxy.ts` optimistic only; Better Auth's `admin` plugin not used.                                                                                                                                                                                    |
| Manual "mark paid"                               | Does not exist. Online confirmation needs a `CAPTURED` attempt fetched from the provider or already recorded; COD collection is an explicit, amount-checked, audited payment transition (§5.10). Payment and fulfilment states are separate machines.                                                                                                                                                                                        |
| Stock restored for goods never received          | Delivery failure and COD refusal never touch inventory; stock returns only through inspection adjustments with an actor and reason (§5.11); the system restock exists only for unshipped cancellations (CHECK on adjustment kinds).                                                                                                                                                                                                          |
| Refund abuse                                     | ADMIN with re-auth; amount bounded by captured − refunded; executed by the Phase 6 queue with provider references; reason required; owner emailed; rate-limited per actor.                                                                                                                                                                                                                                                                   |
| Destructive actions by mistake                   | Confirmation pages with reason and typed order number / product slug; archive instead of delete; deletes only when nothing references the row; re-auth for the irreversible ones.                                                                                                                                                                                                                                                            |
| Stock corruption                                 | Adjustments lock the row and are refused below `reserved`; every adjustment records before/after/reserved/reason/actor (CHECK-enforced); `reserved` is never edited; sales stay in the Phase 6 service.                                                                                                                                                                                                                                      |
| PII exposure to staff                            | Masked by default; reveals need an ADMIN-issued, scoped, time-limited grant (≤ 24 h, SQL ceiling), are themselves time-boxed and re-checked on every render, and end the moment the grant is revoked; order addresses visible only while fulfilling; webhook payloads and outbox recipients masked; audit snapshots redacted; request IPs hashed; exports ADMIN with re-auth and audited.                                                    |
| Audit tampering or loss                          | Append-only table protected twice: an immutability trigger and the runtime role having no `UPDATE`/`DELETE`/`TRUNCATE` privilege (verified in CI by attempting both as that role); SUCCESS rows commit with the change; REFUSED/FAILED rows written after rollback in their own transaction; no secrets or free-text error messages stored; retention indefinite (money records).                                                            |
| Upload abuse                                     | Signatures only for staff with `catalogue.images`, recorded in a ledger, bound to a fixed per-product folder, server-generated `public_id`, `resource_type=image`, `allowed_formats`, an incoming `c_limit` transformation and a signed upload preset enforcing size and dimension caps at Cloudinary; the upload response's own signature is verified and its facts checked against `adminPolicy.uploads` before anything is stored (§5.2). |
| Orphan sweep deleting the wrong assets           | The sweep never lists Cloudinary; it deletes only public ids from our ledger in `ISSUED` state older than the grace period (24 h), each `LIKE 'madhuyamini/products/%'` by CHECK; `ATTACHED` rows are never touched; every deletion is audited as `system:upload-sweep`; a failed destroy is recorded and retried the next day.                                                                                                              |
| CSRF                                             | Server Actions (origin-checked); the CSV export route is GET with no side effects.                                                                                                                                                                                                                                                                                                                                                           |
| Promote script misuse                            | Local DB or explicit production confirmation, verified email required, typed confirmation, audit row, sessions revoked, no HTTP exposure (§13).                                                                                                                                                                                                                                                                                              |
| Enum migration                                   | `ALTER TYPE … ADD VALUE` cannot run inside a transaction with other statements that use the value; the migration adds values in their own statements first (Prisma emits them separately).                                                                                                                                                                                                                                                   |

### 7.1 Failure scenarios

| #   | Scenario                                                            | Handling                                                                                                                                                                                                           |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Staff member loses the authenticator                                | Recovery code (single use) → sign in → regenerate secret and codes. Codes also lost → an ADMIN resets their 2FA (re-auth, audited); the last ADMIN with no access → the promote script on another account (§13).   |
| 2   | Two ADMINs demote each other at the same moment                     | Advisory lock serialises; the second sees one ADMIN left and is refused; the trigger refuses any path that slips through.                                                                                          |
| 3   | A request with a revoked session is in flight                       | Sessions and verifications are read from the database on every request; the next request after revocation fails `requireStaffSession`; nothing cached grants access.                                               |
| 4   | Clock drift between authenticator and server                        | ±1 step tolerance; the accepted step still advances so a drifted code cannot be replayed.                                                                                                                          |
| 5   | The same TOTP code submitted twice at once (double-click, two tabs) | Both requests validate the code; only one conditional UPDATE returns a row; the other is refused and audited `REFUSED`; the session is verified once.                                                              |
| 6   | The same recovery code submitted from two devices at once           | One `UPDATE … WHERE used_at IS NULL` wins; the loser is refused; the user and owner are emailed once.                                                                                                              |
| 7   | Crash between the accepted-step UPDATE and the verification insert  | Impossible: both are in one transaction; a crash rolls both back and the code is accepted again on retry (same step).                                                                                              |
| 8   | `ADMIN_TOTP_KEY` rotated                                            | Old ciphertexts decrypt with the previous key by `keyVersion` and are re-encrypted on the next successful verification; a missing key refuses staff sign-in with a clear server-side error (customers unaffected). |
| 9   | Business transaction fails after the operator confirmed             | Rolled back; a `FAILED` audit row records the attempt; the page shows the typed error; nothing partial persists.                                                                                                   |
| 10  | Audit insert fails inside the transaction                           | The whole operation fails; the operator retries; alert via the server log (Phase 10 monitoring).                                                                                                                   |
| 11  | Someone with the runtime connection tries to edit the audit log     | `permission denied` from the grant before the trigger ever runs; CI proves it.                                                                                                                                     |
| 12  | Runtime role missing locally                                        | The migration's conditional `REVOKE` is skipped; the trigger still protects the table; CI always creates the role.                                                                                                 |
| 13  | Cloudinary upload succeeded but attach was refused or failed        | The ledger row stays `ISSUED`; after 24 hours the sweep destroys exactly that public id and marks it `SWEPT`; a destroy failure is kept with `sweepError` and retried.                                             |
| 14  | Upload response tampered by the browser                             | Response signature check fails → refused; dimensions/bytes/format/folder outside policy → refused; the ledger row remains `ISSUED` for the sweep.                                                                  |
| 15  | Grant revoked while a reveal is on screen                           | The next render re-reads the grant and masks the fields; the audit shows the revocation and the reveal that preceded it.                                                                                           |
| 16  | COD refused at the door                                             | `cod_refused` + `DELIVERY_FAILED`; nothing restocks; the parcel is tracked back; inspection restocks or writes off with an actor and reason.                                                                       |
| 17  | Parcel never comes back (carrier lost it)                           | ADMIN confirms loss with the claim reference; write-off adjustments; refund for captured payments; the order ends `CANCELLED (DELIVERY_FAILED)`.                                                                   |
| 18  | Returned parcel is damaged                                          | Inspection records restock 0 / write-off n per item with a note; a captured payment is still refunded in full unless an ADMIN reduces it with re-auth and a reason.                                                |
| 19  | COD collected recorded by mistake                                   | ADMIN `cod_collection_reversed` with reason; both transitions audited; revenue reports follow the current state.                                                                                                   |
| 20  | Refund retried twice by two admins                                  | Reset is idempotent on a `FAILED` row; the worker claims with `SKIP LOCKED`; the provider reference prevents a second refund (Phase 6).                                                                            |
| 21  | Re-auth code accepted but the original form was lost                | By design: re-auth never replays the original request; the operator submits it again within the window.                                                                                                            |
| 22  | Inventory adjustment races a checkout                               | Both lock the inventory row; the adjustment is checked against the current `reserved` under the lock; the checkout's conditional update sees the new stock.                                                        |
| 23  | Promote script run against the wrong database                       | Production requires `ADMIN_PROMOTE_CONFIRM=<email>` matching the argument and prints the database host for confirmation; a local URL needs no confirmation.                                                        |

- **Without JavaScript:** every action is a form post; the image uploader degrades to "paste an existing Cloudinary URL" with alt text.

## 12. Implementation sequence

1. **Foundation and the gate:** migration 7 + rollback; `admin-policy.ts`; `authz.ts` with `reauth` flags; `runAudited` + redactors; TOTP module, enrolment, verification, recovery codes, re-auth page; `requireStaffSession`; admin shell, layout gate, proxy matcher; promote script and dev-seed admin; transitions extended (fulfilment, COD events). Tests, including the gate matrix and audit atomicity.
2. **Orders and fulfilment:** list/detail with masking rules, processing/ship/deliver, notes, admin cancel with restock adjustments and refund intent, COD collected/reversed, the return-to-origin workflow (delivery failed incl. COD refused, parcel returned, inspection with restock/write-off adjustments, carrier loss), emails. Tests.
3. **Payments and refunds:** review queue and investigation, attach/accept/cancel-and-refund, refunds (create, retry, external), refund operations page. Tests.
4. **Operations monitoring:** jobs, outbox, webhooks, alerts; retries and run-now; the upload orphan sweep in `cleanup`. Tests.
5. **Catalogue and inventory:** products, options/variants, images with hardened signed uploads, categories; inventory levels and adjustments. Tests.
6. **Customers and reports:** masked lists and detail, grants and reveals, role change, 2FA reset; report queries (including returns and write-offs) and CSV export. Tests.
7. **E2E, docs (admin.md §16, roadmap, data-model, auth.md, architecture, CLAUDE.md), gates, commit.**

The second factor is part of step 1 because nothing in the admin area is reachable without it. Each step ends with green gates and a commit; steps 2–3 are front-loaded because they touch money.

## 14. Acceptance criteria

1. Every gate passes with real output; CI green; migration 7 applied and rolled back on the test database with zero drift (enum values documented as non-reversible).
2. No admin action changes money or stock without an audit row in the same transaction; a test proves it for each action.
3. An order cannot be confirmed by the admin without a captured attempt or the COD method, proven by tests that try.
4. STAFF cannot perform any ADMIN-only capability through the UI or a direct action call; CUSTOMER cannot reach any admin page or action; proven by tests.
5. Admin cancellation restores stock exactly and queues a refund for captured payments; the refund worker completes it with the fake gateway.
6. Retries never bypass the workers: a retried row is processed by the same job code.
7. Reports agree with hand-computed figures on fixtures; the storefront still shows no "best-selling" claim.
8. axe reports zero violations on every admin page; every action is keyboard-operable and works without JavaScript except the direct-to-Cloudinary uploader, which degrades to URL entry.
9. Phases 1–6 behaviour unchanged: existing tests pass unmodified (additions only).
10. No staff session reaches an admin page or action without a second-factor verification row for that session; replayed codes are refused; sensitive operations require a fresh code; all proven by tests.
11. Every refused or failed admin operation leaves an audit row even though its business transaction rolled back, and no audit row contains a secret, token, raw payload or unmasked contact detail; proven by tests and a redactor unit suite.
12. STAFF see masked customer data by default; every reveal is audited; proven by tests.
13. Every inventory adjustment row carries kind, reason, actor (or order for system restocks), and before/after quantities consistent with its delta, enforced by CHECKs.
14. A refused, unclaimed or lost parcel never restores stock; stock returns only through inspection adjustments with an actor, proven by tests that attempt the shortcut.
15. Concurrent submissions of the same TOTP code or recovery code yield exactly one acceptance, proven under `Promise.all`.
16. The runtime database role cannot update or delete audit, adjustment or event rows (privilege and trigger), proven in CI; every admin data and service function requires a `StaffContext`, proven by the signature scan and the forged-context suite.
17. Reveal grants are scoped and time-limited, every reveal references its grant in the audit log, and revocation masks the data on the next render, proven by tests.
18. The orphan sweep deletes only ledger-recorded public ids inside the application's folder after the grace period, proven with a recording fake client.

## 17. Implementation notes (1 November 2026)

Phase 7 was built in the seven gated steps of §15 (commits `437caa1`, `d25021e`, `a2f9c27`, `c901bc5`, `467f788`, `18f0c72` and the closing commit). Where the implementation settled a detail the proposal left open, or deviated from it for a reason found during the build, the decision is recorded here.

### 17.1 Gate and audit

- **One audit write per success.** `admin_audit_log` is append-only (trigger plus the runtime role's privileges), so `runAudited` cannot create a row first and fill in snapshots later. It generates the audit id up front, hands it to the work (inventory adjustments store it in `audit_id`, a plain column with no foreign key so the row can be written last), and inserts the `SUCCESS` row as the final statement of the same transaction. `REFUSED` and `FAILED` rows are written in their own transaction after the rollback, as designed.
- **Trigger error code.** The immutability trigger raises with the default SQLSTATE (`P0001`) rather than `restrict_violation`: Prisma maps class-23 codes to its foreign-key error and hides the message, whereas `P0001` reaches the application and the tests as "table … is append-only".
- **Outcomes.** `REFUSED` means authorisation: a missing capability, a stale second factor, or a reveal without an active grant. A business rule that refuses inside the work (a transition that does not apply, an amount that does not match, stock that would undercut held units) rolls back and is recorded as `FAILED` with its error code, so the two can be told apart in the audit browser.
- **The admin layout and the URL.** Layouts cannot read the request path, so `proxy.ts` overwrites a request header with it on every `/admin` request; the layout uses it only as the return path after sign-in or re-authentication, through `safeReturnPath`.
- **Operations that must talk to a provider** (re-check, attach a payment, external refunds, run a job, verification resend, CSV export) use `runAuditedExternal`: authorise first, run with no transaction open, record afterwards. Their inner writes keep their own transactions.

### 17.2 Orders, payments and stock

- **Captured amount as evidence.** A mismatch leaves the attempt's own amount untouched (Phase 6), so the captured amount comes from the `payment.captured` event the capture recorded. Refund ceilings, the underpayment check in "accept mismatch" and the refund queue all use that evidence.
- **Partial refunds.** An attempt becomes `REFUNDED` only once processed refunds cover the captured amount; earlier refunds leave it `CAPTURED` so further refunds remain possible. The fake gateway now refuses a refund beyond the captured amount and marks the payment refunded only when the total reaches it, like the provider.
- **Inspection.** Units received back enter stock as `RESTOCK_ON_RETURN` (+received), then damaged units leave it as `WRITE_OFF` (−damaged), so the ledger shows both what came back and what was lost; both rows carry the inspector, the reason and the audit id.
- **Carrier loss** records no inventory rows: the units never came back, so stock is genuinely unchanged. The loss is on the shipment (claim reference), the order event (per-SKU quantities) and the audit snapshot (`writtenOff`), and the customer is refunded.
- **Cash on delivery.** A delivery failure on a COD order records `cod_refused` on the attempt whatever the failure reason; the failure reason itself is on the shipment. Collection needs the exact amount and a delivered order, or a reason at handover.
- **Deleting catalogue rows.** Because the stock ledger is immutable, a variant with any movement (including its initial stock) and a product containing one cannot be deleted; they are archived or deactivated, which is the A3 rule applied consistently.
- **Order address views** are logged once per staff member and order, on the first render of a detail page in a fulfilment state.

### 17.3 Customers

- **Revocation is enforced at read time.** Every render of a customer page re-reads the grant behind each live reveal; a revoked or expired grant masks the fields immediately. Reveal rows are not rewritten on revocation (the `expires_at > created_at` CHECK would otherwise be violated when both fall in the same instant).
- **Role changes** take the `user-roles` advisory lock, require the target's email typed back, revoke sessions, staff verifications and grants in the same transaction, clear the second factor on demotion to `CUSTOMER`, and leave the last-admin rule to the database trigger (surfaced as a failed operation with its message).

### 17.4 Uploads and images

- Signatures bind `timestamp`, the per-product `folder`, a server-generated `public_id`, `allowed_formats`, the `c_limit` transformation and, when `CLOUDINARY_UPLOAD_PRESET` is set, the signed preset. The response signature and facts are verified before anything is stored; the stored URL is built from the public id and version, never taken from the browser.
- Without Cloudinary credentials (development), images can be added by `https` address with their dimensions and description; such rows have no public id and are never swept.
- The enrolment page shows the setup key and an `otpauth://` link rather than a QR image: no image library was added, and every authenticator app accepts a typed key.

### 17.5 Seeds, scripts and tests

- `SEED_ADMIN_PASSWORD` creates `admin@example.com` (ADMIN) and `staff@example.com` (STAFF) in development and CI, clearing their second factor and sessions on every seed so the e2e journeys always start at enrolment. `scripts/provision-db-roles.sql` must run before `prisma migrate deploy` on a fresh database (CI does).
- The e2e admin journeys create their own staff accounts over plain SQL (`e2e/staff.ts`): the generated Prisma client is ESM-only and the Playwright runner cannot load it. They cover the gate, enrolment, a new-session verification with a recovery code, axe on every admin page, a cash-on-delivery order shipped, refused, returned and inspected, and a grant issued (after re-authentication), used and revoked.
- Final counts at the closing commit are in the Phase 7 completion report and in `docs/roadmap.md`.

### 17.6 Still open after Phase 7

- Reports do not yet "time-travel": refunds are attributed to the period they were processed in, cancellations to the period cancelled in.
- Staff cannot yet see their own grants in one place; grants are listed on the customer they cover and in the audit browser.
- The customer page reveals one field set at a time; a second reveal within the window extends nothing, it adds a new ten-minute window for its own fields.

### 18.2 Verified without change

- **TOTP and sessions:** replay protection is a conditional update on `lastAcceptedStep`; verification is per session row; re-authentication after ten minutes; ten concurrent submissions of one code yield one verification (existing tests).
- **Audit:** `runAudited` writes `SUCCESS` last in the work's transaction, `REFUSED`/`FAILED` after rollback; `admin_audit_log`, `inventory_adjustments` and `order_events` refuse `UPDATE`/`DELETE` by trigger and by the `madhuyamini_app` role's privileges; snapshots pass `redactForAudit` (no e-mail, phone, address, password or token fields reach the log).
- **Grants:** scoped to one customer and named fields, at most 24 hours (CHECK), re-read on every render so revocation masks the very next request; reveal rows carry the grant id.
- **Uploads:** signatures bind folder, public id, formats and transformation; the response signature is checked; the sweep deletes only ledger `ISSUED` rows inside `madhuyamini/products/` (CHECK); `ATTACHED` rows are never touched.
- **Privileges:** `scripts/provision-db-roles.sql` grants the runtime role table-level rights only; migrations run as the owner through `MIGRATION_DATABASE_URL`; the integration tests `SET ROLE madhuyamini_app` and prove the denials.
- **Permissions:** `gate-signature.test.ts` requires every exported data and service function under `features/admin` to take a `StaffContext` (or, for the six pre-gate flows, a `CurrentUser`); the gate matrix refuses no, forged, CUSTOMER, unverified STAFF and STAFF-for-ADMIN contexts on reads as well as writes.

### 18.3 Gate fallout

- The complete gate was run three times on the audited tree. The first run found the staff-directory regression above (four e2e failures, fixed with the test that now pins it). The second run failed once, in one browser project only, on axe's `document-title` rule for the inspection page: Next.js streams metadata after the initial UI, so right after a client-side navigation the document can be a moment without its `<title>`. `expectNoAxeViolations` now waits for a non-empty title before analysing; a page that never sets one still fails, with a clearer message. The third run passed.

### 18.4 Residual production risks

- **Return refunds are whole.** §9's "reduce a return refund" (ADMIN deducts for damage before the refund is queued) is not implemented; inspection queues the full captured amount. Deductions need a partial refund in place of the automatic one.
- **Double refunds** were closed on 2 November 2026 (§18.5).
- **Reads are refused by redirect, not recorded.** An unauthorised page view ends at sign-in or at the enrolment page with no `REFUSED` row; the gate matrix proves the refusal, and mutations are always recorded.
- **Key retirement is gradual.** After a rotation, `ADMIN_TOTP_KEY_PREVIOUS` must stay set until every staff member has verified once (rows re-encrypt on the first accepted code); unconfirmed enrolments under the old key expire within fifteen minutes.
- **Width and height** of an upload are still reported by the browser; Cloudinary's response signature covers the public id and version only. The signed preset now required in production enforces the limits at Cloudinary.
- **Per-user limits** bound one account; an attacker spraying many staff accounts is bounded per account and by `two-factor:ip`, not globally.
- **Unchanged from §16:** Razorpay test-mode smoke, hosted database roles, secrets (including `ADMIN_TOTP_KEY` and the Cloudinary preset), scheduler, backups and monitoring remain the owner's pre-launch list.

### 18.5 Follow-up: refund idempotency (2 November 2026)

The remaining refund risk from §18.4 is closed. Admin refunds are idempotent per operation, duplicate operations are refused by the database, and the balance is validated under the order lock on creation and on retry.

- **Keys.** `OrderActions` renders a fresh `operationKey` (UUID) into every refund form; `createRefundSchema` requires it; `createRefund` stores it on the `refunds` row (`operation_key`, unique, migration `20261102150000_refund_operation_keys` with `rollback.sql`). Automatic refunds (cancellation, inspection, late capture) keep `NULL`; their idempotency is the `reference`, as in Phase 6.
- **Repeats.** Under the order lock, `createRefund` first looks the key up: the same key with the same order and amount returns the existing refund (`reused: true`, audited as `SUCCESS` with `reused` in the snapshot, notice "already queued … nothing new was created"); the same key with another amount or another order is refused with `REFUND_KEY_CONFLICT`. The disabled submit button is now a courtesy only.
- **Balance.** Creation reads `refundableAttempts` under the lock (unchanged from Phase 7) so concurrent refunds with different keys cannot add up to more than was captured; `retryRefund` now applies the same check, because other refunds may have used the balance since the first attempt failed. Retries keep their `reference`, and the `refund-payments` job asks the provider for that reference before requesting anew (Phase 6), so a lost response never refunds twice.
- **Tests** (`tests/integration/admin-payments.test.ts`, "refund idempotency"): concurrent submissions with one key (double click) queue one refund with one email; a retried and a repeated request return the existing refund, and a changed amount or another order is refused; the unique index refuses two rows with one key; three concurrent refunds with different keys that each exceed half the capture leave exactly one; three partial refunds settle the payment only once they reach the captured amount, and a fourth paise is refused; a failed refund frees its amount and its retry is refused once that amount is used again; a retry after a lost response finds the provider's refund by reference and creates no second one. The e2e journey (`e2e/admin.spec.ts`, "refunds") submits the real form twice with the same key and once with a changed amount.
