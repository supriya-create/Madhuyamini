# Phase 8: Returns, Exchanges and Custom Madhubani Artwork

Status: **proposal, revision 1 (2 November 2026), awaiting the owner's approval.** Design and documentation only: no application code, schema, migration, dependency or environment change accompanies this document. Implementation begins only after approval and only in the gated steps of §13.

Scope: customer-initiated returns and exchanges for delivered orders, item-level refunds on top of the Phase 6 refund worker and the Phase 7 refund operation keys, and a quotation-based custom artwork (commission) workflow. Out of scope here, though listed under "Phase 8" in `docs/roadmap.md`: coupons (the refund arithmetic in §4 is written so coupons can arrive later without reworking it), verified-purchase reviews, and linking guest orders to later accounts. Policy pages (Phase 9) are a go-live dependency of returns and are named where they bite.

Conventions: amounts are integer paise; every duration, limit, percentage and size lives in a policy file with a literal-scan test; every admin mutation runs through `runAudited` / `runAuditedExternal`; every customer mutation is a Server Action validated with Zod and scoped by ownership in the service. Identifiers in backticks are the existing ones found in the code during inspection, not proposals, unless marked **new**.

## 2. Objectives, principles and non-goals

**Objectives.** A customer whose order was delivered can ask to return some or all units, with reasons and photographs, and follow the request to a refund or a replacement; staff can approve, instruct, receive, inspect and decide per unit without ever touching stock or money outside the audited paths; refunds are computed per unit from the order snapshot and never exceed what the provider captured; a customer can commission a piece of Madhubani art through a quotation that becomes an order only on acceptance and payment.

**Principles.**

1. **Nothing moves by itself.** Submitting a return request changes no stock and no money. Stock moves only at inspection, through `applyAdjustment`; money moves only through `queueRefundIntent` and the refund worker, after an explicit decision.
2. **One engine each.** Inventory: `features/inventory/service.ts`. Refunds: `features/payments/refunds.ts` plus the worker. Orders, payments and shipments for anything that is sold or shipped: the Phase 6/7 order path. This phase adds state machines around them, not alternatives to them.
3. **Snapshots are immutable.** `orders`, `order_items`, `payments`, `refunds`, `inventory_adjustments`, `order_events`, `admin_audit_log` are never edited. Return, exchange and commission tables reference them.
4. **Every amount and duration is policy.** Two new policy files; a unit test rejects literals elsewhere, as today.
5. **Every mutation is audited and idempotent.** Admin: `runAudited` with a target type and redaction allow-list. Customer: operation keys on anything that creates money-bearing or stock-bearing rows (return requests, acceptances), unique in the database.
6. **Privacy by default.** Evidence and reference images are private assets with signed, expiring delivery URLs; staff see customers masked; commission messages are not e-mail threads but stored, rate-limited, ownership-checked records.

**Non-goals.** Coupons; verified-purchase reviews; marketplace-style multi-artist payouts (artist assignment is internal record-keeping, not a payment system); carrier API integration (tracking is recorded, not synchronised, unless D8.17 approves a carrier); automatic approval of returns; store credit as a general currency (exchange credit exists only inside an exchange).

## 3. Customer returns

### 3.1 Eligibility

Evaluated by a pure function `returnEligibility(order, items, policy, now)` in **new** `features/returns/rules.ts`, unit-tested like `features/checkout/rules.ts`. Inputs are the order snapshot and the live `returns-policy.ts` values; the result is per line: `eligible`, or a reason code.

| Rule               | Source                                                                                                                                        | Ineligible reason code    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| Order status       | `orders.status = DELIVERED` and `shipments.delivered_at` set. `CANCELLED`, `RETURNED`, in-progress fulfilment, `NEEDS_REVIEW`: no.            | `ORDER_NOT_DELIVERED`     |
| Window             | `now ≤ delivered_at + policy.windowDays` (D8.1). The window is evaluated at **submission**, never re-evaluated later for an open request.     | `WINDOW_CLOSED`           |
| Category           | `products.category_id` not in `policy.nonReturnableCategorySlugs` (resolved to ids at startup and cached; D8.2) and not a commission product. | `CATEGORY_NOT_RETURNABLE` |
| One-of-a-kind      | `products.is_one_of_a_kind`: returnable unless the category says otherwise (default returnable; D8.2 may differ for originals).               | (category rule)           |
| Quantity           | `requestedQty ≤ quantity − already returned or in an open return for this line` (computed from `return_items`, §7.2).                         | `QUANTITY_EXCEEDED`       |
| Open request       | At most `policy.maxOpenRequestsPerOrder` (recommended 1) open return request per order; a second request waits until the first closes.        | `REQUEST_ALREADY_OPEN`    |
| Exchange target    | Only when exchanges are enabled for the category (D8.4) and the requested variant is `is_active` with available stock at submission time.     | `EXCHANGE_NOT_AVAILABLE`  |
| Damaged on arrival | Reason `DAMAGED_ON_ARRIVAL` or `WRONG_ITEM` ignores the category rule but still requires evidence (D8.2, D8.5). Window still applies.         | (none)                    |
| Account            | The order's `user_id` equals the signed-in user. Guest orders: see D8.3; until approved, guests are told to contact support.                  | `ORDER_NOT_FOUND`         |

The policy file (**new** `src/config/returns-policy.ts`, shape mirrors `admin-policy.ts`):

```ts
returnsPolicy = {
  windowDays, // D8.1
  nonReturnableCategorySlugs, // D8.2
  evidence: { requiredForReasons, maxImages, minImagesForDamage },
  approval: { staffDecisionDays, customerShipByDays, receiveByDays }, // expiry clocks (§10.1)
  shippingRefund: { mode }, // D8.6: "never" | "when_shop_at_fault" | "always"
  returnShipping: { payer }, // D8.5: "customer" | "shop" | "shop_when_at_fault"
  deductions: { maxPercentOfLine }, // ceiling for damage deductions (D8.7)
  exchanges: { enabled, sameProductOnly, differenceMaxInPaise }, // D8.4
  cod: { refundMethod }, // D8.8: "bank_transfer_manual" | "upi_manual"
  limits: {
    requestPerUser,
    requestPerIp,
    uploadPerRequest,
    messagePerRequest,
    withdrawPerUser,
  },
  maxOpenRequestsPerOrder,
  retention: { closedRequestEvidenceDays }, // §7.9
};
```

### 3.2 States of a return request

```
DRAFT? (not persisted) ─submit─► REQUESTED ─approve─► APPROVED ─mark shipped (customer or staff)─► IN_TRANSIT ─receive─► RECEIVED ─inspect─► INSPECTED ─settle─► CLOSED
REQUESTED ─request info─► INFO_REQUESTED ─customer replies─► REQUESTED
REQUESTED | INFO_REQUESTED ─reject─► REJECTED (closed)
REQUESTED | INFO_REQUESTED | APPROVED ─customer withdraws─► WITHDRAWN (closed)
APPROVED ─ship-by clock lapses─► EXPIRED (closed)        IN_TRANSIT ─receive-by clock lapses─► OVERDUE (open; alert)  ─receive─► RECEIVED  |  ─declare lost─► LOST (closed; §3.5)
RECEIVED ─short shipment─► RECEIVED (items marked NOT_RECEIVED; inspection continues)
```

`CLOSED` means every item has a final decision and every money movement decided (queued or refused); the request's `settled_at` is set. Refund execution continues asynchronously in the refund worker, visible on the request through the linked `refunds` rows.

Transitions are table-driven (`features/returns/transitions.ts`, `nextReturnStatus(current, event)`) with the same unit-test style as `transitions.ts`.

### 3.4 Special cases

| Case                                                | Handling                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One item from a multi-item order                    | The request lists that line only; other lines stay untouched; the order remains `DELIVERED`. Refund is per §4 for that line, shipping per D8.6 (shipping is refunded, if at all, only when every unit of the order has been returned and accepted, unless the shop is at fault).                                                                  |
| Multiple quantities of the same variant             | `requested_qty` on one `return_items` row; approval, receipt and inspection carry per-unit counts (`restock_qty + repair_qty + quarantine_qty + write_off_qty + return_to_customer_qty = received_qty`). Refund = unit allocation × accepted units (§4.3).                                                                                        |
| Delivered damaged                                   | Reason `DAMAGED_ON_ARRIVAL` requires `minImagesForDamage` photographs; eligible regardless of category; return shipping payer = shop (D8.5); no damage deduction may be applied to a `DAMAGED_ON_ARRIVAL` line (the deduction form refuses it); shipping refund per D8.6 "at fault".                                                              |
| Part of an order, then the rest later               | Allowed while the window is open and no request is open for the order. Line availability subtracts closed-and-accepted and open quantities. ## 4. Item-level refunds and financial correctness

### 4.1 What the engine already guarantees

`queueRefundIntent` writes an `INITIATED` row with a unique `reference`; `refund-payments` executes it, asks the provider for an existing refund with that reference before creating one, retries with backoff, gives up to `FAILED` with an owner alert, and settles the attempt as `REFUNDED` only when processed refunds cover the captured amount. Admin refunds carry `operation_key` (unique), replay returns the existing refund, the balance is read under the order lock, and `retryRefund` re-checks the balance. **Phase 8 changes none of this.** It adds:

- a nullable `refunds.return_request_id` (FK) so a refund is traceable to the return that caused it, and `RefundReason` value `customer_return` (and `exchange_difference`, §5.3);
- a **calculation layer** (`features/returns/refund-calculation.ts`, pure, unit-tested) that turns per-unit decisions into one amount per payment attempt plus an itemised breakdown persisted as `return_refund_lines`;
- the settlement operation (R10), which is the only caller of `queueRefundIntent` for returns, under the order lock, with an operation key.

### 4.2 Allocation of order-level amounts to units

Definitions, all integer paise, taken from the order snapshot:

- `L_i = order_items.line_total_in_paise` for line `i`, `q_i = quantity`, `S = subtotal_in_paise = Σ L_i`.
- `D = discount_in_paise` (0 today; coupons or exchange credit later), `H = shipping_in_paise`, `F = cod_fee_in_paise`, `T = total_in_paise = S + H + F − D`.
- `C_a = capturedAmountInPaise(attempt a)` (evidence from the `payment.captured` event; for COD, the collected amount on the attempt).

**Discount allocation (largest-remainder method, deterministic):**

```
share_i      = floor(D × L_i / S)                       for every line, in order_items order (ascending variant id)
remainder    = D − Σ share_i                            (0 ≤ remainder < number of lines)
```

The `remainder` paise are added one each to the lines with the largest fractional parts `(D × L_i mod S)`, ties broken by ascending variant id. Result: `Σ discounted_i = S − D` exactly, where `discounted_i = L_i − share_i`. Per unit: `unit_i = floor(discounted_i / q_i)`, `unit_remainder_i = discounted_i − unit_i × q_i` (0 ≤ it < `q_i`); the **last** `unit_remainder_i` units of the line carry one extra paisa, so that returning all `q_i` units refunds exactly `discounted_i`, and returning `k` units refunds `k × unit_i + max(0, k − (q_i − unit_remainder_i))`.

These functions (`allocateDiscount`, `unitValues`) are pure, table-tested with the examples in Appendix A, and shared by the account page (to show "you will receive about ₹…"), the admin breakdown and the settlement.

### 4.3 Refund amount for a settlement

For each line `i` with accepted units `k_i` (decisions RESTOCK, REPAIR, QUARANTINE, WRITE_OFF when the fault is the shop's, and per D8.7 also WRITE_OFF when the customer's fault but a full refund is still granted), the gross refund is `G_i = value of k_i units` per §4.2. Deductions:

- `damage_i ≤ min(G_i, floor(G_i × deductions.maxPercentOfLine / 100))`, allowed only with `deduction_reason` from a fixed list and at least one staff photograph attached to the item (R9 evidence), never on `DAMAGED_ON_ARRIVAL` or `WRONG_ITEM` lines; recorded on `return_refund_lines` with the evidence ids.
- Shipping: `H_refund ∈ {0, H}` per D8.6 and the "every unit of the order accepted" rule (§3.4); recorded as its own breakdown line.
- COD fee `F`: never refunded (it paid for a service rendered), unless D8.6 says otherwise; its own line with amount 0 by default.
- Return shipping charged to the customer (D8.5 "customer" with a shop label): `R_ship = returnShipping.labelChargeInPaise`, its own negative line.

```
refund_total = Σ (G_i − damage_i) + H_refund − R_ship
```

Caps, applied in this order and each producing a visible breakdown line when it bites:

1. `refund_total ≥ 0`, else 0 (nothing is ever charged through a return).
2. `refund_total ≤ Σ_a (C_a − refunded_a)` over `refundableAttempts(order)` (what the provider still holds for this order).
3. `refund_total ≤ T − Σ already refunded for the order − Σ exchange credit already consumed` (the order's remaining monetary value; prevents a replacement order's credit and a refund from both consuming the same units).

The amount is then split across captured attempts largest-remaining first (an order normally has one captured attempt; two exist only after review flows) and queued with `queueRefundIntent` per attempt, sequence from `refundCount + 1`, `operationKey` = `${settlement operation key}:${attemptNo}` (the settlement form carries one key; attempts derive deterministic sub-keys so a replay reproduces the same set). All of this runs under `lockOrder`, after re-reading `refundableAttempts`, in the same transaction as the status change to `CLOSED`. A refund that later `FAILED` in the worker leaves the request `CLOSED` and the refund visible on the admin refund queue with `retryRefund` (unchanged) and the existing balance re-check; the customer page shows "refund in progress" until `PROCESSED`.

### 4.4 Multiple partial refunds, concurrency and duplicates

- Several returns on one order produce several settlements, each its own refund rows; the engine's sequencing (`-R1-2`, `-R1-3`) and the cap in §4.3 keep the sum within the capture. Settlement holds the order lock, so two settlements (or a settlement and an admin `createRefund`) serialise and the second sees the first's rows.
- Double submission of a settlement: the operation key on `return_requests.settlement_operation_key` (unique) plus the status guard (`INSPECTED → CLOSED` conditional update) make the second call return the existing result; `refunds.operation_key` unique is the backstop.
- Admin "goodwill" refunds through the existing form remain possible and are counted by the caps.

### 4.5 Refund states as seen from a return

| `refunds.status`        | Return page shows                  | Admin shows                                                                          |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| `INITIATED`             | Refund queued                      | Queue position; the worker will request it                                           |
| `REQUESTED`             | Refund requested from the provider | Provider refund id; polled until processed                                           |
| `PROCESSED`             | Refunded on <date>                 | Done; attempt `REFUNDED` once fully covered                                          |
| `FAILED`                | Refund delayed; we are on it       | Retry (balance re-checked) or mark refunded externally (verified with `listRefunds`) |
| Unknown (provider lost) | As above                           | `recheck` tools and `listRefunds` reconciliation, unchanged                          |

### 4.6 Cash on delivery

COD orders have a `CAPTURED` COD attempt with the collected amount but no provider to refund through. Settlement of a COD return records a **`manual_refunds`** row (**new**, §7.4): amount from §4.3, method per D8.8 (bank transfer or UPI, details captured from the customer in the return form, stored encrypted like TOTP secrets under `ADMIN_TOTP_KEY`? No: under a **new** `CUSTOMER_DATA_KEY`, see §8.3, and masked for staff), status `PENDING → PAID | CANCELLED`, `paid_at`, `paid_reference`, `paid_by`. Marking paid is an ADMIN sensitive operation with the transfer reference typed in; nothing automatic touches bank accounts. COD attempts never become `REFUNDED`; the manual refund is the record. Reports count manual refunds separately.

### 4.7 Payment status and fulfilment status stay independent

A return never changes `orders.status` or `payments.status` by itself: a `DELIVERED` order with three returns is still `DELIVERED`; its attempt becomes `REFUNDED` only through `settleAttemptIfFullyRefunded` when processed refunds reach the capture. Exchange replacement orders have their own payment status. The admin order page lists returns, refunds and replacement orders side by side.

### 4.8 Audit

Every settlement writes: the audit row (`return.settled`, before/after snapshots with the breakdown totals, redacted), `return_refund_lines` (the arithmetic, immutable), `order_events` `return.refund_queued` per refund, the refund rows (engine), and for COD the `manual_refunds` row. Deductions carry reason, evidence ids and the staff member. Nothing about bank details appears in the audit snapshot (allow-list).

## 5. Exchanges

### 5.1 Architecture options

| Option                                                                               | How it would work                                                                                                                                                                                                                                                                        | Why not / why                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A. Add replacement lines to the original order                                       | New `order_items` on the same order, a second shipment.                                                                                                                                                                                                                                  | Breaks three invariants: `order_items` is an immutable snapshot, `@@unique([orderId, variantId])` forbids the same variant twice, `shipments.order_id` is unique. Totals and the capture comparison would no longer describe the order. **Rejected.**                                                                                                                                |
| B. A free-standing exchange fulfilment (exchange items shipped from their own table) | `exchange_items` with their own shipping, stock and payment handling.                                                                                                                                                                                                                    | Duplicates reservation, commit, shipment, delivery, cancellation, e-mails and reports; a second fulfilment engine. **Rejected.**                                                                                                                                                                                                                                                     |
| C. **Linked exchange record plus a replacement order**                               | `exchanges` row ties a return request to a **new `orders` row** (`kind = EXCHANGE_REPLACEMENT`, `exchange_of_order_id`) created at settlement with the replacement lines at current prices, credit from the returned units as `discount_in_paise`, and the difference as the amount due. | Reuses placement internals, reservations/commits, payment attempts (a positive difference is paid through the existing pay page), shipments, fulfilment, cancellation with restock, e-mails and reports without change. Needs a `kind` column, a credit-only payment method for zero-due replacements, and a placement entry point that does not start from a cart. **Recommended.** |

### 5.2 The exchange lifecycle

```
return item preference EXCHANGE ─approve (R5)─► (no stock action) ─inspect (R9): item accepted─► settle (R10):
   replacement available  → exchanges row OPEN + replacement order created (PENDING_PAYMENT if difference > 0, else CONFIRMED with stock committed)
   replacement unavailable→ item settles as refund; exchanges row not created; customer told (return.closed says why)
replacement order CONFIRMED ──existing fulfilment──► SHIPPED → DELIVERED   ⇒ exchanges.status FULFILLED (set by the delivery transition, same transaction)
replacement order PENDING_PAYMENT ──payment timeout / customer cancel (existing)──► CANCELLED ⇒ exchanges.status LAPSED; the credit is refunded through the original order (§5.3, automatic at the cancellation transaction)
replacement order CANCELLED by admin before shipping (existing cancelOrder, restock) ⇒ exchanges.status CANCELLED; credit refunded likewise
replacement delivered and the customer returns it ⇒ an ordinary return on the replacement order (its snapshot is the truth; no special case)
```

`exchanges.status`: `OPEN → FULFILLED | LAPSED | CANCELLED`. The row is created in the settlement transaction and updated in the replacement order's own transitions (one extra statement in `markDelivered` and in the cancellation paths, guarded by `kind = EXCHANGE_REPLACEMENT`).

### 5.3 Money in an exchange

For each exchanged item: `credit_i = G_i − damage_i` (the unit value the customer would have been refunded, §4.3). Replacement line value `P_i = current variant price × k_i` (prices are read live at settlement, like placement). Shipping on the replacement: `H_x` per D8.10 (recommended: free when the shop is at fault, otherwise the standard `shippingCharge` over the replacement subtotal). Then:

```
replacement.subtotal  = Σ P_i
replacement.shipping  = H_x
replacement.discount  = min(Σ credit_i, subtotal + shipping)          ← exchange credit, written to discount_in_paise
replacement.total     = subtotal + shipping − discount                 (orders_total_consistent holds)
credit_surplus        = Σ credit_i − replacement.discount              (≥ 0)
```

- `total > 0`: the replacement is a `PENDING_PAYMENT` order with `payment_method = RAZORPAY`, a reservation for its lines (`reserveForOrder`, `ttlMinutes` from the checkout policy), and the customer pays the difference on the existing `/checkout/pay/[orderId]` page. A difference above `exchanges.differenceMaxInPaise` is refused at settlement (the customer is offered a refund instead). `payment.minOrderInPaise` applies: a difference below ₹1 is rounded **down to zero in the customer's favour** by raising the credit (documented in the breakdown).
- `total = 0`: `payment_method = STORE_CREDIT` (**new** enum value, allowed only with `total_in_paise = 0` by CHECK), status `CONFIRMED` immediately, stock sold with `commitForOrder` (conditional; failure means the stock went between inspection and settlement, and the item falls back to refund in the same transaction), order events and the confirmation e-mail as for COD.
- `credit_surplus > 0`: refunded through the **original** order's refund path in the same settlement (`queueRefundIntent`, reason `exchange_difference`, operation sub-key `:surplus`), subject to the caps of §4.3. The credit consumed by the replacement is recorded on `exchanges.credit_applied_in_paise` so cap 3 in §4.3 sees it.
- A replacement that lapses or is cancelled before shipping: in that cancellation transaction (original order locked first, then the replacement, §9.4), queue a refund of `credit_applied_in_paise` on the original order (reason `exchange_difference`, operation key derived from the exchange id), restock the replacement lines through the existing `releaseOrderHolds` / `restockForOrder`. If the customer had paid a difference, that payment is refunded by the replacement order's own cancellation refund (existing code path, unchanged).

The original return request's refund lines record the exchange: a `return_refund_lines` row of kind `EXCHANGE_CREDIT` with a negative amount and the replacement order number, so the customer's breakdown reads "value of returned items ₹X, applied to replacement order MY-… ₹Y, refunded ₹Z".

### 5.4 Stock, duplicates and failures

- No stock is held between request and settlement (D8.4 explains the trade-off: holding for weeks starves the storefront; the customer is told stock is confirmed at inspection).
- Settlement reserves or commits through the inventory service in lock order; `StockUnavailableError` on any replacement line converts **that item** to a refund inside the same transaction and records why.
- Exactly one replacement per return item: `exchange_lines.return_item_id` unique; `exchanges.replacement_order_id` unique; the settlement operation key makes the whole settlement idempotent. The replacement order has `cart_id = null`, so the one-live-order-per-cart index does not apply; its `orders_one_exchange_per_return_item` guarantee is the unique index above.
- Replacement orders are listed in the admin order list with a badge and a link to the return; the customer sees them in the account order list with "replacement for MY-…". They cannot be exchanged again as a "same exchange"; a return on them is a new, ordinary return.
- Different-product exchanges (D8.4): the mechanics above do not care which variant is chosen; the policy flag `sameProductOnly` restricts the customer form. Recommended: same product only in Phase 8.

### 5.5 Placement entry point

Checkout placement (`features/checkout/service.ts`) starts from the request's cart and a `quoteHash`. Settlement needs the same order creation without a cart. The proposal is an internal refactor, behaviour-preserving and covered by the existing Phase 6 tests: extract the "create the order rows, items, reservation or commit, first attempt, events, outbox" part into `features/orders/placement.ts` `createOrderFromLines(tx, input)` where `input` carries the user, contact and address snapshot, lines with live prices, shipping, discount, `kind`, `payment_method`, and the parent references. `placeOrder` calls it after cart validation and the quote check; settlement and commission acceptance (§6.6) call it directly. This is the one Phase 6 file this phase touches, and the refactor lands as its own step with the full Phase 6 integration suite as the gate (§13, step 8.0).

## 6. Custom Madhubani artwork (commissions)

### 6.1 Shape of the workflow

```
REQUESTED ─staff review─► IN_REVIEW ─questions─► INFO_REQUESTED ─customer reply─► IN_REVIEW
IN_REVIEW ─decline─► DECLINED (closed)              customer ─withdraw─► WITHDRAWN (closed, until a deposit exists)
IN_REVIEW ─assign artist, issue quotation v1─► QUOTED ─customer rejects─► QUOTE_REJECTED → (staff may issue v2) QUOTED | DECLINED
QUOTED ─quotation expires─► QUOTE_EXPIRED → (staff may re-issue) QUOTED | closed
QUOTED ─customer accepts (creates the deposit instalment order)─► AWAITING_DEPOSIT ─deposit captured─► IN_PRODUCTION
AWAITING_DEPOSIT ─deposit order times out / cancelled─► QUOTED (acceptance void; a new acceptance creates a new deposit order)
IN_PRODUCTION: production stages (SKETCH → PREVIEW_SHARED → CUSTOMER_APPROVED | REVISION_REQUESTED (bounded) → PAINTING → QUALITY_CHECK → READY)
READY ─balance instalment order created─► AWAITING_BALANCE ─balance captured─► READY_TO_DISPATCH ─ship (balance order's shipment)─► DISPATCHED ─deliver─► DELIVERED (closed)
Any open state ─cancel (customer or shop; policy per stage, D8.14)─► CANCELLED (closed; refunds per D8.14 through the instalment orders)
```

A **quotation is never an order.** The order rows that carry money are **instalment orders** (`kind = COMMISSION_INSTALMENT`) created only on acceptance (deposit) and on readiness (balance). Each instalment order has one line: the commission's own catalogue product (§6.4), priced at the instalment amount. Everything that already works for orders (payment attempts, capture verification, timeouts, refunds, shipments, e-mails, reports, admin review) applies without change.

### 6.2 Categories and pricing rules without hard-coding

**New table `custom_artwork_categories`** (admin-managed, ADMIN `artwork.categories`): `slug`, `name`, `description`, `is_active`, `dimension_presets` (JSON list of `{ label, widthCm, heightCm }` plus `allowsCustomDimensions`), `intended_uses` (JSON list of labels), `style_options` (JSON list), `base_price_hint_in_paise` (shown to staff as a starting point, never to customers as a price), `deposit_percent`, `included_revisions`, `quotation_validity_days`, `lead_time_days_min/max`, `returnable` (D8.15 default false), `cancellation_rule` (enum: `BEFORE_PRODUCTION_FULL_REFUND`, `BEFORE_PRODUCTION_LESS_FEE`, `NO_REFUND_AFTER_APPROVAL`, …, D8.14), `cancellation_fee_percent`, `sort_order`. Validation of these JSON fields with Zod at the service boundary; the form is the admin catalogue style.

Each request snapshots the category's rules at **quotation** time into `custom_artwork_quotations` (deposit percent, included revisions, validity, lead time, cancellation rule, returnable), so later category edits never change an open commission. Global guard-rails (minimum deposit percent, maximum validity, upload limits, rate limits, reminder cadences) live in **new** `config/commissions-policy.ts`; a category cannot go outside them (Zod refinement on save).

### 6.3 Request, review and clarification

- **Request form** (`/custom-artwork`, signed-in customers; guests see the page and are asked to sign in or register first, D8.16): category, dimensions (preset or custom within category limits), intended use, preferred colours (free text, bounded), style, description (bounded), up to `limits.referencesPerRequest` reference images (private uploads, §8.3), consent checkbox to the commission terms (text from the policy page when Phase 9 lands; until then, a short in-page statement that no obligation exists before a quotation is accepted). Rate-limited per user and per IP. Operation key on the request (unique) against double submission.
- **Review queue** (STAFF `artwork.view`, `artwork.review`): newest first, filters by status, category, assigned artist; the customer masked as everywhere.
- **Clarification** through `custom_artwork_messages` (both directions, bounded length, rate-limited for the customer, visible on both sides, append-only). Staff questions move the request to `INFO_REQUESTED`; a reply moves it back. No free e-mail threads: the outbox sends "you have a message" notices with a link.
- **Decline** (STAFF, audited, reason list) closes the request.
- **Artist assignment** (`custom_artwork_requests.assigned_artist_id` → `artists` table, **new**, admin-managed: name, bio, active flag, specialities; ADMIN `artwork.assign`). The customer sees the artist's name only if the artist profile is marked public (Phase 9 "artists" pages reuse this table). No payouts are modelled (non-goal); a `commission_share_percent` field exists only if D8.12 asks for record-keeping.

### 6.4 Quotation

`custom_artwork_quotations` is **versioned and immutable**: `(request_id, version)` unique; a new version supersedes (`superseded_by_id`). Fields: itemised lines (`custom_artwork_quotation_lines`: description, quantity, unit amount, amount; e.g. painting, framing, packaging, shipping, GST line if the owner's accountant requires it, D8.13), `subtotal`, `shipping`, `tax` (if applicable), `total`, `deposit_in_paise` (= `ceil(total × deposit_percent / 100)` rounded **up** to the paisa, and never below `payment.minOrderInPaise`), `balance_in_paise = total − deposit`, `estimated_days`, `valid_until`, the snapshot of category rules, `issued_by_id`, `issued_at`, `status` (`ISSUED → ACCEPTED | REJECTED | EXPIRED | SUPERSEDED`), `customer_note` on rejection. Issuing is STAFF with `artwork.quote`; amounts above `commissionsPolicy.quoteAdminAboveInPaise` require ADMIN (sensitive). The e-mail `artwork.quoted` links to the quotation page; the page shows the lines, totals, validity, what the deposit covers, cancellation and return terms as snapshotted.

When a quotation is issued, the service also creates the request's **commission product**: a `products` row with `kind = COMMISSION` (**new** column), `status = DRAFT` forever (storefront reads expose only `ACTIVE`, so it is invisible), slug `commission-<requestNumber>`, one variant with `sku = CMN-<requestNumber>`, `price_in_paise = 0` (the instalment orders set the line price explicitly from the quotation, not from the variant), `inventory.stock_on_hand = 0`. It exists so that `order_items.variant_id` (required, `Restrict`) has a legitimate target and reports can group commissions by product kind. The commission product is created once per request (`custom_artwork_requests.product_id` unique) and reused across quotation versions.

### 6.5 Acceptance, deposit and the instalment orders

Acceptance (customer, operation key, `QUOTED` and `valid_until ≥ now` checked under the request lock): the same transaction

1. marks the quotation `ACCEPTED` with `accepted_at` and the acceptance's operation key (`custom_artwork_acceptances`, append-only: who, when, which version, IP hash, user agent hash, the terms snapshot id);
2. creates the **deposit instalment order** through `createOrderFromLines` (§5.5): `kind = COMMISSION_INSTALMENT`, `commission_request_id`, `instalment = DEPOSIT`, one line (commission variant, quantity 1, unit price = `deposit_in_paise`), shipping 0, `payment_method = RAZORPAY` (COD not offered for commissions, D8.11), address = the customer's chosen delivery address (snapshot, needed later for the balance order and shipment), `pending_expires_at` per the checkout policy, and a first payment attempt as in checkout;
3. moves the request to `AWAITING_DEPOSIT` and e-mails `artwork.deposit_due` with the pay link.

Inventory: the commission variant's stock is 0 and `createOrderFromLines` is told `stock: "none"` for commission lines (no reservation, no commit); the order CHECKs do not involve stock. The capture of the deposit order (existing `applyCapture`, compared to the order total = deposit) fires a **commission hook** in the same transaction (`features/commissions/hooks.ts`, called from the capture path where `kind = COMMISSION_INSTALMENT`): request → `IN_PRODUCTION`, `deposit_paid_at`, event, e-mail `artwork.production_started`. If the deposit order times out (existing `expire-reservations` sweep cancels `PENDING_PAYMENT` orders past the deadline; for commission orders there are no holds to release) the hook on cancellation returns the request to `QUOTED` (if the quotation is still valid) or `QUOTE_EXPIRED`; the acceptance row stays as history.

The **balance instalment order** is created by staff at `READY` (`artwork.production`, audited): same mechanics, line price = `balance_in_paise` (plus any approved change orders, §6.7), delivery address copied from the deposit order unless the customer updated it through a message (staff edit, audited). Capture → `READY_TO_DISPATCH`. Shipment and delivery use the balance order's `shipments` row through the existing `shipOrder` / `markDelivered`; the delivery transition fires the hook → request `DELIVERED`. If the balance is zero (deposit 100 %), the balance order is created with `payment_method = STORE_CREDIT` and `total = 0`, confirmed at once, so the shipment still has an order to belong to.

### 6.6 Why instalments are orders

One capture equals one order total (`applyCapture` compares amount and currency to the order; a mismatch is `NEEDS_REVIEW`). Modelling a deposit and a balance as two captures on one order would require changing that comparison, the attempt uniqueness (one open attempt per order), the refund ceilings and the reports. Two small orders keep every Phase 6 invariant intact and give each payment its own receipt, timeout, review flow and refund path. The cost is two order numbers per commission, which the customer page hides behind "deposit" and "balance" labels with the commission reference as the headline.

### 6.7 Design preview, approval, revisions and change orders

- Staff upload previews as private assets (purpose `ARTWORK_PREVIEW`, §8.3) attached to a `custom_artwork_previews` row (`version`, `caption`, `uploaded_by_id`); the customer sees them through signed, expiring URLs on the commission page.
- **Approval** is a customer action with an operation key that writes `custom_artwork_approvals` (**append-only, immutable**: request, preview version, `approved_at`, IP hash, user agent hash, the preview's Cloudinary `public_id` and `version` and the SHA-256 of the preview bytes as recorded at upload). The approved version is what production follows; later previews need a new approval.
- **Revision requests**: customer action with a bounded message; counted against `included_revisions` from the quotation snapshot. Beyond that, staff may issue a **change order** (`custom_artwork_change_orders`: description, amount, status `PROPOSED → ACCEPTED | REJECTED`, accepted with an operation key) whose accepted amount is added to the balance instalment. Staff may also waive the limit (audited).
- **Production stages** are rows in `custom_artwork_production_events` (append-only): stage enum, note, optional private photograph, by whom. Reminders (§10.1) use the latest stage timestamp.

### 6.8 Cancellation and refunds

Rules are the quotation's snapshot of the category policy (D8.14). Mechanics are always the same: cancellation (customer: operation key; shop: ADMIN sensitive, audited) closes the request and, per the rule, queues refunds on the instalment orders through `queueRefundIntent` (reason `commission_cancelled`, amounts computed by a pure function from the snapshot: full deposit, deposit less a percentage fee, or nothing), under the instalment order locks, capped by their captures. A deposit order still `PENDING_PAYMENT` is cancelled through the existing `cancelPendingOrder` path (no refund needed). Returns of delivered commissions are governed by the snapshot's `returnable` flag: when true, the balance order (or the deposit order when there is no balance) is eligible for the §3 flow like any order; when false, the return form is not offered and the account page explains the commission terms.

### 6.9 Privacy of files

Reference images, previews and production photographs are uploaded as Cloudinary `type = authenticated` (or `private`) assets under `madhuyamini/commissions/<requestId>/…` and `madhuyamini/returns/<requestId>/…`, never under `products`. They are never rendered through the public `image/upload` loader; pages render **signed delivery URLs** generated server-side per request with `commissionsPolicy.files.urlTtlMinutes` expiry, only after the ownership check (customer: the request's `user_id`; staff: capability `artwork.files` or `returns.view`). Downloads of originals go through a single authenticated route handler `/api/files/[ledgerId]` that checks ownership and redirects to a short-lived signed URL (one new HTTP path, justified: it keeps the signature logic in one place and lets the audit log record staff downloads of customer files as `file.downloaded`).

### 7.5 Candidate entities not adopted

`ReturnInspection` / `ReturnInspectionItem`: inspection results are columns on `return_items` plus `return_events` (one inspection per request; re-inspection is modelled as a correction event by ADMIN with reason, never an edit of quantities after settlement). `ExchangeItem`: `exchange_lines` (same concept). `CustomArtworkReference`: `customer_uploads` with purpose `ARTWORK_REFERENCE`. `CustomArtworkRevision`: `custom_artwork_messages` of type revision plus `revisions_used`; the bounded count is the business rule, not a table. `CustomArtworkProduction`: `custom_artwork_production_events`. `CustomArtworkPaymentSchedule` and `CustomArtworkShipment`: orders and shipments (§7.4).

### 7.6 Integrity rules the database enforces

Beyond the CHECKs above: foreign keys with `Restrict` wherever a row is financial evidence (orders, items, refunds, acceptances, approvals); `Cascade` only from a request to its own children (items, messages, events, lines), and only because the request itself is `Restrict`-protected by refunds and orders; partial unique indexes for "one open request per order", "one accepted quotation per request", "one deposit/one balance order per commission", "one replacement per return item"; immutability triggers (migration 7 function reused: `refuse_mutation()` with `P0001`) on `return_events`, `return_messages`, `return_refund_lines`, `custom_artwork_messages`, `custom_artwork_acceptances`, `custom_artwork_approvals`, `custom_artwork_production_events`, `custom_artwork_quotation_lines`, plus a column-level trigger on quotation amounts; the runtime role gets no `UPDATE`/`DELETE` on those tables.

### 7.7 Migration and rollback strategy

- Three migrations in step order (`8.1`, `8.3`, `8.5` in §13), each applied with `prisma migrate deploy` (the dev database) and by the integration global setup (the test database), as today. `rollback.sql` per migration drops the new tables and columns in dependency order and leaves enum values in place (documented). Rollback of `phase8_returns` is refused by `Restrict` FKs while refunds reference return requests; the rollback file states that those rows must be exported and detached first, which is the correct protection for financial records.
- `orders.kind` default `STANDARD` backfills existing rows at `ADD COLUMN … DEFAULT` (PostgreSQL 11+ does this without rewriting the table).
- Storefront read paths add `kind = 'CATALOGUE'` to product queries in the same step as `products.kind` (a failing integration test "commission products never appear in storefront reads" guards it).
- Seeds: dev-only artist, one commission category, no fake commissions or returns (fixtures live in tests only).

### 7.8 Indexes summary

Listed per table above; the hot paths are the account page (returns by user), the admin queues (status + due clocks), availability arithmetic (`return_items.order_item_id`), upload sweeps (`status, issued_at`) and reminder jobs (`status, updated_at`).

### 8.3 Files

- **Issue**: `issueCustomerUploadTicket(user, purpose, targetHint)` (customer; rate-limited `uploadPerRequest`, `uploadPerUserPerDay`) and `issueStaffUploadTicket(ctx, purpose, target)` (audited). Signed parameters bind `timestamp`, `folder` (`madhuyamini/returns/<requestId>` or `madhuyamini/commissions/<requestId>`; for a not-yet-submitted return, a per-user draft folder `madhuyamini/returns/draft/<userId>` that the submit step re-targets by Cloudinary `rename`, or, simpler and recommended, the request row is created first as `DRAFT` and the folder is final from the start), server-generated `public_id`, `type = authenticated`, `allowed_formats`, the `c_limit` transformation, and the signed preset required in production (§18 of `docs/admin.md`).
- **Attach**: the response signature is verified (`expectedResponseSignature`), facts checked against `commissionsPolicy.files` / `returnsPolicy.evidence` (formats, bytes, dimensions), ownership checked (the ledger row's `owner_user_id` is the caller and its `status = ISSUED`), `sha256` stored when the provider returns it (`etag`) or computed by fetching the asset once server-side for approvals.
- **Deliver**: only signed URLs (`sign_url` with expiry) rendered by server components after the ownership check; `next/image` is not used for private assets; the route handler `/api/files/[ledgerId]` is the single download path (authenticated, ownership-checked, audited for staff, `Cache-Control: private, no-store`).
- **Never**: public delivery types, URLs taken from the browser, listing the Cloudinary account, deleting outside our folders (the sweep's `isWithinUploadFolder` check extended to the two new prefixes).
- **Encryption at rest for beneficiaries**: AES-256-GCM with a **new** `CUSTOMER_DATA_KEY` (same key schema and rotation pattern as `ADMIN_TOTP_KEY`), production-required when COD manual refunds are enabled.

### 8.5 Threats and mitigations

| Threat                                                   | Mitigation                                                                                                                                                                                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IDOR on return, commission, file or message ids          | Owner-scoped data access; request numbers resolved with `userId`; file ledger rows checked for owner or capability; integration tests for "another user", "anonymous", "staff without capability".                            |
| Over-refund by crafted quantities or amounts             | Quantities validated against `order_items.quantity` minus accepted and open; amounts never accepted from the client (the settlement form carries decisions, the server computes); caps in §4.3; DB CHECKs on quantities.      |
| Duplicate refunds (double click, retry, two staff)       | Operation keys unique on `return_requests.settlement_operation_key` and `refunds.operation_key`; order lock; status conditional updates; existing worker idempotency by reference.                                            |
| Stock inflation through repeated inspections             | One inspection per request (status guard `RECEIVED → INSPECTED` conditional update); corrections are ADMIN, audited, and expressed as explicit `CORRECTION` adjustments with the request id in the reason.                    |
| Exchange fulfilled twice                                 | `exchange_lines.return_item_id` unique, `exchanges.replacement_order_id` unique, settlement idempotent.                                                                                                                       |
| Quotation accepted after expiry or after a newer version | Acceptance checks `status = ISSUED`, `valid_until ≥ now`, and that the version is the request's `current_quotation_id`, all under the request row lock; partial unique "one accepted per request".                            |
| Deposit paid against a changed quotation                 | The deposit order snapshots the amount; the quotation's amounts are immutable (trigger); a new version requires a new acceptance and a new deposit order.                                                                     |
| Private images leaked by URL                             | Authenticated delivery type, signed URLs with short TTL, never cached publicly, never in e-mails (e-mails link to the page).                                                                                                  |
| Malicious uploads (oversized, wrong type, polyglot)      | Signed preset enforces size and formats at Cloudinary; response facts verified; no server-side processing of bytes beyond hashing; `Content-Disposition: attachment` on the download route.                                   |

| Abuse: request flooding, message spam                    | Rate limits (§8.4), bounded lengths, one open request per order, decline/withdraw paths.                                                                                                                                      |
| Staff collusion on refunds                               | Settlement is ADMIN with a fresh second factor, every line evidenced and audited; per-actor limits; reports show refunds by actor; deductions require evidence ids.                                                           |

| Beneficiary data exposure                                | Encrypted at rest, last4 only in the UI, reveal audited, nulled after retention.                                                                                                                                              |
| CSRF / session                                           | Server Actions with Next's origin checks, existing session handling; no new cookies; the download route is GET, idempotent, and leaks nothing without a session.                                                              |

## 9. Inventory and fulfilment integration

### 9.1 When returned units become stock

Only at inspection (R9) and only for units decided `RESTOCK`, through `applyAdjustment` `RESTOCK_ON_RETURN` with `orderId` = the original order, `actorId` = the inspector, `auditId` = the inspection's audit row, in ascending variant id within the transaction. Available stock rises immediately (`stock_on_hand += n`; `reserved` untouched), so the storefront can sell the unit at once.

### 9.2 Quarantine, repair and write-off

- `QUARANTINE` and `REPAIR` units do **not** move inventory; they are counted on `return_items.held_qty`. The admin inventory page shows "held from returns" per variant (a query over `return_items`), so the figure is visible without a second stock counter.
- Release from hold (STAFF `inventory.adjust`, audited `return.hold_released`): `applyAdjustment` `RESTOCK_ON_RETURN` (+n, reason references the request) and `held_qty −= n`, `released_qty += n`, in one transaction; or `WRITE_OFF` decision recorded (no stock movement, `held_qty −= n`, `write_off_qty += n`). Phase 7's rule holds: a `WRITE_OFF` adjustment (−n) is only written when the unit **had** re-entered stock; a unit written off straight from inspection never touched stock and gets no adjustment row, only the item decision (this matches `completeInspection`, which restocks `received` first and then writes off; for customer returns the cleaner equivalent is to restock only `RESTOCK` units, so write-offs leave no ledger row and the return item is the record).
- `RETURN_TO_CUSTOMER` (ineligible unit arrived): no stock movement; an outbound `return_shipments` row records the parcel back.

### 9.3 Exchanges and stock

At settlement, replacement lines are reserved (`reserveForOrder`, difference due) or sold (`commitForOrder`, zero due). Failed commit → that item becomes a refund in the same transaction. A lapsed replacement releases holds through the existing expiry sweep; a cancelled confirmed replacement restocks through `restockForOrder` (`RESTOCK_ON_CANCEL`). Returned units of the original order are restocked by the inspection regardless of the exchange outcome.

### 9.4 Lock order and serialisation

Extended lock order, honoured by every transaction in this phase:

```
carts → orders (original first, then replacement/instalment, ascending id if several) → return_requests / custom_artwork_requests (FOR UPDATE)
      → payments/refunds → inventory (ascending variant id) → reservations
```

Concurrent inspections of one request: the second blocks on the request row lock and then fails the `RECEIVED → INSPECTED` guard. Concurrent inspection and admin `applyAdjustment` on the same variant: serialised by the inventory row lock inside `applyAdjustment`. Concurrent settlement and admin refund: serialised by the order lock. Two replacements for one item: unique index. Integration tests pin each of these (§12).

### 9.5 Shipments

Inbound return parcels: `return_shipments` (customer- or staff-recorded, tracking recorded, not synchronised unless D8.17). Outbound replacement and commission shipments: the existing `shipOrder` / `markDelivered` on the replacement or balance order, which already e-mail the customer and record events; their delivery transition updates `exchanges.status` or the commission status in the same transaction.

## Appendix A: allocation examples (integer paise)

**A1.** Two lines, `L = [129_900, 259_800]`, `q = [1, 2]`, `S = 389_700`, discount `D = 10_000`.
`share = [floor(10_000 × 129_900 / 389_700), floor(10_000 × 259_800 / 389_700)] = [3_333, 6_666]`, remainder `1` → goes to the line with the larger fractional part (line 1: `0.333…` vs line 2: `0.666…` → line 2). `discounted = [126_567, 253_133]`, sum `379_700 = S − D`. Units: line 2 `unit = 126_566`, `unit_remainder = 1` → the last unit carries `126_567`. Returning one unit of line 2 refunds `126_566`; both: `253_133`.

**A2.** Shipping `H = 9_900` on an order whose two lines are both returned and accepted: `H_refund = 9_900` (D8.6 "every unit accepted"); if only one line, `0`.

**A3.** Damage deduction with `maxPercentOfLine = 30`: `G = 126_566`, `damage ≤ 37_969`.

**A4.** Cap 2: captured `C = 389_700 + 9_900 = 399_600` on one attempt, an earlier goodwill refund of `50_000` processed; a settlement computing `379_700 + 9_900 = 389_600` is capped at `349_600` with a `CAP_PROVIDER_BALANCE` line of `−40_000`.

**A5.** Exchange: returned unit credit `126_566`; replacement variant now `139_900`; shipping free (shop at fault): `subtotal 139_900`, `discount 126_566`, `total 13_334` → `PENDING_PAYMENT`, paid online. Replacement `129_900` with credit `126_566`: `total 3_334`. Replacement `119_900`: `discount 119_900`, `total 0` → `STORE_CREDIT`, surplus `6_666` refunded on the original order.

**A6.** Deposit: quotation total `1_250_000`, deposit 50 % → `625_000`; with 33 % → `ceil(412_500) = 412_500`; total `1_000_001` at 50 % → `ceil(500_000.5) = 500_001`, balance `500_000`.
